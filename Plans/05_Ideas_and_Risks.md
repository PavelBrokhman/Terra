## Потенциальные проблемы / риски

### R1. Пространственный масштаб (огромный + плотный + 3D)
- **Сейчас:** разреженный hash-грид (`SpatialGrid`, broad-phase) + distance-check (narrow-phase). Память ∝ числу организмов; пустые области стоят 0. Для console/2D — ок.
- **Риск:** при большом радиусе зрения broad-phase сканирует много ячеек (eyesight 120px → ~33×33 ячейки на организм на тик). При больших плотных мирах — горячая точка по CPU.
- **Идеи на потом:** octree/quadtree (иерархия), индексация крупных организмов по нескольким ячейкам (сейчас — только по центральной), пространственный шардинг (MMO-зоны). Не сейчас — на 3D/мультиплеер.

### R2. Float сломает детерминизм (guardrail)
- **Никогда** не переходить на float-координаты: плавающая точка не бит-в-бит воспроизводима между машинами/компиляторами → рушит replay и горячий резерв (#7, prepare-now #1).
- Нужна суб-пиксельная точность → **только fixed-point** (целые в масштабе), не float. Сейчас координаты целые — так и держать.

### R3. Reproduce-кулдаун не виден поведению
- `can_reproduce` (и `DefaultHerbivore`, и DSL) не знает про `ReproductionWait` → зрелое сытое существо тратит ходы на отказную попытку размножиться вместо еды. Заметно на коротких прогонах (≤ кулдауна).
- **Идея:** пробросить «готов размножаться» (или сам `ReproductionWait`) в `IWorldView`/`OrganismSnapshot` — починит и встроенные поведения, и DSL.

### R4. Изоляция загружаемого поведения
- DLL-путь (как legacy) в .NET Core **без CAS** → загруженный код доверенный, не изолирован. Для одиночного локального — ок; для мультиплеера нужна изоляция.
- Текущий DSL-путь (text-file) изолирован by design (нет исполнения чужого кода). Микросервис/Docker — изоляция контейнером. Учитывать при выходе в сеть.

### R5. Туши при масштабе
- Туши живут `TimeToRot` тиков и участвуют в collision/запросах. При больших популяциях — рост числа объектов. Сейчас ок; следить при масштабировании.

### R6. Стоимость broad-phase скана зрения
- `SpatialGrid.Query` на каждый организм каждый тик при большом зрении = много dict-lookup'ов. Связано с R1. Возможный фикс: кэш видимости/реже пересчитывать при длинных тиках.

## Идеи на будущее

### I1. Богаче DSL поведения
- **Сейчас:** одно сигнал-условие на правило, фиксированный словарь сигналов/действий.
- **Потом:** составные условия (AND/OR/NOT), числовые сравнения (`energy < 30`), доступ к параметрам мира/существа, параметризованные действия. Цена — парсер выражений.

### I2. DLL-адаптер поведения (legacy-стиль)
- Второй адаптер `IOrganismBehavior` поверх `AssemblyLoadContext` — для тех, кто хочет писать существ на C#, как в оригинале. Контракт уже единый, добавляется рядом с DSL.

### I3. Микросервис-адаптер поведения
- Третий адаптер: сервер шлёт «ситуация → действие» внешнему сервису (Lua/Python/Docker). Жизнеспособен из-за длинных тиков (#10). Для продвинутых/изолированных существ.

### I4. Динамические поля среды
- Реализовать энергополя/параметры среды (`solar`/`oxygen`/`density`, #8/#9, `03`-док) как разреженные слои поверх той же сетки. Динамические (меняются по тикам), не статичный MMO-heightmap.

### I5. Живой текстовый вид (progress-view)
- Кроме ленты событий — компактная ASCII-карта/сводка, перерисовка по тикам, чтобы «прогресс видно». Без графики. Отдельный презентер на том же event stream.
