# God-Sim — Design Review и решения (надстройка над планом модернизации)

> Статус: **зафиксированные решения** (vision владельца проекта, согласовано в обсуждении).
> Это надстройка над [Terrarium2.0_Modernization.md](Terrarium2.0_Modernization.md) — она **расширяет** видение
> от «экосистема организмов» к **multiplayer god-sim движку**. Базовый принцип (логика отделена от
> презентации, движок знает только контракт поведения) сохраняется и усиливается.

---

## Что это

Проект эволюционирует в **multiplayer god-simulator**: много богов (users) на одной общей территории.
Движок — детерминированная машина исполнения правил; вся «интеллектуальность» и поведение задаются
пользователями декларативно. Никакого хардкода видов или поведения внутри ядра.

---

## Зафиксированные решения

| # | Тема | Решение |
|---|------|---------|
| 1 | **North Star** | Multiplayer god-sim — много богов (users) на общем мире. Объединяет god-sim механику (лепка мира + задание видов через правила) с multiplayer-видением. |
| 2 | **Жизненный цикл** | Мир появляется по запросу. Бог проверяет условия → выбирает свои entity → шлёт запрос на участие → получает **территорию** (random или по preference) → спавнит новые сущности. |
| 3 | **Авторитет / сеть** | **Сервер-авторитетный**. Любой клиент может сам стать хостом мира. Юзер передаёт серверу **изменения поведения** (правила), а не двигает сущности сам. Связь — REST API / линк к серверу мира. *Мечта (явно «нереально», но желаемо):* тяжёлый клиент (VM / 3D-десктоп с полной копией) может стать **co-owner / горячим резервом** — подхватывает мир, если главный сервер падает. |
| 4 | **Тип мира** | Связывает **контракт действий/физики + рендеринг** (console / 2D / 3D / web / mobile). У бога — **свой пул entity под каждый тип мира**. Несовместимая по действиям entity в мир не ставится. |
| 5 | **Размерность** | **Канон 3D-пространство + время (tick)**. Рендер — это **проекция**: 3D → как есть, 2D → уронить ось, console → текст. Размерность ≠ тип рендера (console может рендерить 3D-grid как текст). |
| 6 | **Авторинг поведения** | **Структурированные правила (DSL/JSON)** — `IF condition THEN actions PRIORITY n`, интерпретатор. Реализуется как `RuleInterpreter : IOrganismBehavior`. Песочница by design (нет произвольного кода), детерминировано, bounded. Компилируемый C# **отпадает**. |
| 7 | **Ядро** | **Детерминированное + журнал команд (command-sourcing)** с самого начала. Каждое изменение мира = запись в журнал → replay, сохранения, отладка, и будущий горячий резерв «бесплатно». |
| 8 | **Параметры мира** | **Динамическая схема**, задаётся хостом через **wizard** при создании (temperature min/max, gravity, density = atmosphere content, …). Никаких фиксированных полей мира — только **расширяемый реестр параметров**. Параметр, влияющий на механику (высота → скорость по формуле), **автоматически прокидывается** в контракт авторинга entity. |
| 9 | **Абстракция vs terrain** | Абстракция мира = **условия + последствия** (семантика: подъём / плотность воздуха / потолок-теснота → эффекты по формулам), **не геометрия**. Конкретный terrain/объекты (2D/3D-ассеты) — отдельный слой, который **хост сопоставляет** с абстрактными условиями, чтобы видимое совпадало с симулируемым. Ядро картинки не знает. |

## Архитектурная схема

```
┌─────────────────────────────────────────────────────────────┐
│         Simulation Core (детерминированное ядро, 3D+время)    │
│  - Мир: реестр параметров (динамическая схема, wizard)        │
│  - Условия → последствия (формулы)                            │
│  - Tick: sense → decide → apply (двухфазный)                  │
│  - Журнал команд (command-sourcing) → replay / резерв         │
│  - Контракт поведения: IOrganismBehavior (ничего больше)      │
└─────────────────────────────────────────────────────────────┘
        ▲ behavior                       │ events (versioned, JSON-Lines)
        │                                ▼
┌──────────────────┐         ┌──────────────────────────────────┐
│ RuleInterpreter  │         │  Presentation adapter (per type)  │
│  : IOrganismBeh. │         │   console → текст                 │
│  (DSL/JSON юзера) │         │   2D      → проекция + спрайты     │
└──────────────────┘         │   3D      → проекция + terrain-    │
                             │             ассеты + rend. engine  │
                             │             (хост достаёт сам,     │
                             │              сопоставляет с        │
                             │              абстрактными          │
                             │              условиями)            │
                             └──────────────────────────────────┘
```

## Что меняется относительно исходного плана модернизации

- **Этап 2 (авторинг)**: было — компилируемый C# через `AssemblyLoadContext` + Roslyn.
  Стало — **DSL/JSON-правила + интерпретатор**. Это заодно снимает самую тяжёлую legacy-проблему
  оригинала (sandboxing / CAS), т.к. произвольный код не исполняется.
- **Презентационные слои**: были «просто подписчики на events». Уточнено — тип мира **связывает**
  физику и рендер; рендер = **проекция** канонической 3D-абстракции; для тяжёлых типов (3D) хост
  поставляет ассеты + движок-переводчик и **сопоставляет** их с абстрактными условиями.
- **Мир**: был «grid с координатами». Стало — **реестр динамических параметров** + слой
  **условия→последствия**, схема задаётся хостом.

## Prepare-now: что заложить в Этап 1 (cheap now, expensive later)

Это вещи, которые почти бесплатны на старте и мучительны при ретрофите:

1. **Детерминизм** — seeded RNG, прокинутый через весь движок; детерминированный порядок обхода
   сущностей; запрет `DateTime.Now` / `Guid.NewGuid()` / неупорядоченных коллекций в sim-логике.
2. **Command-sourcing** — каждое изменение мира через команду, пишется в журнал; состояние
   воспроизводимо из (seed + журнал). Включает replay, сохранения и будущий горячий резерв.
3. **Двухфазный тик** — `sense → decide → apply`: сущности читают иммутабельный снапшот и возвращают
   **намерение (intent)**; движок применяет и разрешает конфликты отдельной фазой.
4. **Action = намерение, не мутация** — мир меняет **только** движок. Поведение возвращает intent;
   это же ограничивает поведение одним решением за тик (нет зависаний/бесконечных циклов в тике).
5. **Координаты — 3D-вектор** (не `x,y`); рендер через проекцию. Не хардкодить 2D.
6. **Реестр параметров мира** — не фиксированные C#-поля, а расширяемый набор; связь
   «параметр → формула → последствие» через интерфейс (даже если параметров пока 1-2).
7. **`RuleInterpreter : IOrganismBehavior`** — поведение из DSL/JSON за единым контрактом движка.
8. **Версионированный поток событий** (JSON-Lines): `{t, type, actor, target, location, payload}`.
9. **`IWorldView` строго локальный**; его поверхность **выводится из схемы параметров мира**
   (entity видит только те параметры, что мир объявил).

## Этап 1 — конкретный объём (решение: «минимум + швы»)

Цель — рабочий текстовый MVP, который **проверяет ключевую идею** (параметры→механика), но не
переинженеренный.

**Входит:**
- Console-мир (текстовый рендер) над **3D-grid** (Z может быть = 1 на старте, но координата 3D).
- Детерминированное ядро + журнал команд + двухфазный тик.
- 1-2 **захардкоженных параметра** (напр. `elevation → movement speed` по простой формуле),
  но **через правильные интерфейсы**: реестр параметров, `IWorldView`, intent-действия.
- `IOrganismBehavior` + `RuleInterpreter` с минимальным DSL (несколько условий/действий).
- 2-3 reference-организма, заданных через DSL (растение / травоядное / хищник).
- Версионированный event stream → текстовый презентер.

**НЕ входит (швы оставляем, не строим):**
- Полный DSL-движок формул (произвольные пользовательские формулы) — позже.
- Wizard создания мира, REST API, сеть, мульти-хост — Этапы 2-4.
- Реальный terrain / ассеты / 3D-рендер — Этап 3.
- Сопоставление terrain ↔ условия — Этап 3.

**Критерий готовности:** симуляция детерминированно прогоняет N тиков, организмы (DSL) взаимодействуют,
параметр мира реально влияет на механику через формулу, события логируются, журнал команд
воспроизводит идентичный прогон.

## Отложено (явные швы, не строим сейчас)

- Распределение территории богам (взят простой вариант, механизм не финализирован).
- Wizard + динамические пользовательские формулы во всём объёме.
- Сеть / сервер-хост / REST API / горячий резерв (co-owner replica).
- 3D/2D рендер-адаптеры, terrain-ассеты, сопоставление abstraction ↔ terrain.
- Система баланса (influence-budget / энтропия / rule-complexity limits) — из balance-дока.
  *Примечание:* самый острый инженерный риск balance-дока (зависания/недетерминизм user-правил)
  уже снят пунктами prepare-now #3 и #4.
