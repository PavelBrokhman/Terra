## Что это

Microsoft Research Terrarium 2.0 (~2003–2005) — учебная AI-песочница, где пользователи пишут организмы (C#/VB.NET), которые живут в общей экосистеме. Примерно 313 файлов, .NET 2.0, WinForms + DirectX 9, ASP.NET ASMX, SQL Server.

## Ключевой архитектурный принцип: разделение логики и презентации

Движок (ядро симуляции) должен быть **полностью независим** от способа отображения. Это позволит на 1-м этапе обойтись текстовыми логами, а позже подключить любой визуальный слой (2D, 2.5D, 3D, web) без изменения ядра.

```
┌─────────────────────────────────────────┐
│         Simulation Core (Engine)        │  ← чистая логика, без UI
│  - World state (grid, organisms)        │
│  - Tick loop                            │
│  - Organism execution sandbox           │
│  - Event bus (emits domain events)      │
└─────────────────────────────────────────┘
                   │
                   ▼ emits events: OrganismBorn, OrganismMoved, OrganismAte, OrganismDied, ...
                   │
       ┌───────────┴───────────┐
       ▼                       ▼
┌──────────────┐      ┌──────────────────┐
│ Presentation │      │  Presentation    │
│  Layer: TEXT │      │  Layer: 2D/3D    │  (будущие этапы)
│  (Этап 1)    │      │                  │
└──────────────┘      └──────────────────┘
```

Презентационные слои — **подписчики на события**, они не знают о внутренностях движка.

## План по этапам

### Этап 1 — Текстовый MVP (core + text logs)

**Цель**: работающая симуляция с текстовым выводом событий. Ни пикселя графики.

**Что входит**:
- `Engine` — ядро симуляции:
  - Мир как сетка (grid) с координатами
  - Tick-loop (дискретные шаги времени)
  - Event bus: публикует события каждый тик
  - **Движок не знает о конкретных типах организмов** — только о `IOrganismBehavior` интерфейсе
- `TextPresenter` — подписчик на события, пишет строки в stdout/лог-файл
- **`IOrganismBehavior` — единственный контракт поведения**:
  ```csharp
  public interface IOrganismBehavior {
      OrganismAction OnTick(IWorldView sense);
  }
  ```
- Встроенные организмы (растение, травоядное, плотоядное) — это **reference implementations того же интерфейса**. Никакого привилегированного доступа к ядру.

### Принцип: behavior как абстракция с 1-го дня

На 1-х этапах все организмы одного вида будут двигаться одинаково — НО реализовано это должно быть **через тот же `IOrganismBehavior`**, который позже будут писать пользователи.

```
Engine ──► IOrganismBehavior ◄── DefaultHerbivore   (этап 1, встроенный)
                ▲              ◄── DefaultCarnivore  (этап 1, встроенный)
                │              ◄── UserCreature_Bob  (этап 2+, загружается извне)
                │
         движок не различает, кто это
```

**Почему это критично**:
- Интерфейс используется с самого начала (dog-fooding) — к моменту появления user-кода он уже проверен
- Нет «специального пути» для built-ins → нет архитектурного долга
- Замена дефолта на пользовательский код = просто загрузка другой реализации, без изменений в движке
- Встроенные организмы служат **reference implementations** для будущих авторов user-creatures

**Запрещено на этапе 1**: любой код внутри `Engine`, который знает имена конкретных классов организмов или делает `if (organism is Herbivore)`. Движок работает только с `IOrganismBehavior`.

**Пример вывода этапа 1**:
```
[t=0001] World: 10 plants, 3 herbivores, 1 carnivore spawned
[t=0042] Herbivore#7 (4,12) moved → (5,12)
[t=0042] Herbivore#7 ate Plant#3 at (5,12)  [energy: 40 → 65]
[t=0043] Carnivore#1 (8,8) sensed Herbivore#7 at distance 5
[t=0051] Carnivore#1 attacked Herbivore#7 — killed  [energy: 30 → 70]
[t=0100] Stats: plants=7  herbivores=2  carnivores=1
```

**Стек этапа 1**:
- **.NET 8** (console app) — простой старт, кроссплатформенно
- Никаких БД, UI, сети — только in-memory + stdout
- Unit-тесты движка (xUnit)

**Критерий готовности**: симуляция запускается, 2–3 демо-организма взаимодействуют, события логируются, можно прогнать N тиков и получить финальную статистику.

### Этап 3 — Визуализация (подключается к тому же ядру)

Выбор одного из вариантов презентационного слоя:

| Вариант | Стек                                  | Плюсы                          |
|---------|---------------------------------------|--------------------------------|
| 2D десктоп | Avalonia 11 + SkiaSharp            | Кроссплатформенно, быстро       |
| 2D/2.5D web | Blazor WASM + PixiJS / Phaser 3   | Ноль установки, доступность     |
| 3D web    | Three.js / Babylon.js               | Современно, изометрия           |

Ядро не меняется — только новый подписчик на event bus рисует картинку.

## Рекомендация по запуску

Начать с **Этапа 1** как чистого console-приложения на .NET 8. Это даёт:

- Работающую симуляцию за минимум усилий
- Чистую архитектуру, которая переживёт смену UI
- Лёгкость тестирования (всё детерминировано, без графики)
- Возможность позже подключить любую презентацию — десктоп, web, 2D, 3D — без переписывания ядра

Текстовые логи — это не временный костыль, а **постоянный first-class презентационный слой**, который остаётся полезным:

- **Для end-users**: лёгкий режим просмотра «что происходит онлайн» при высокой нагрузке/большом трафике, когда графика тяжёлая или канал узкий. Пользователь может следить за экосистемой как за лентой событий (Twitter-style timeline, server log view).
- **Для мобильных/слабых устройств**: текст работает везде.
- **Для доступности (accessibility)**: screen readers, slow connections.
- **Для отладки, CI, replay-анализа**: детерминированная воспроизводимость.
- **Для стриминга/вещания**: можно транслировать events stream через SSE/WebSocket без рендеринга на сервере.

### Следствия для архитектуры

Раз текстовый поток — продукт для пользователей, а не только для разработчиков, нужно сразу заложить:

- **Стабильный формат событий** (versioned schema, JSON-Lines): `{t, type, actor, target, location, payload}`
- **Фильтры и подписки**: пользователь выбирает что смотреть (только хищники, только свой вид, конкретная зона мира)
- **Human-readable рендеринг поверх raw events**: один и тот же event stream → текстовые строки ИЛИ графика
- **Rate-limiting / aggregation**: при большом трафике агрегировать события (`[t=1000] 42 herbivores moved, 3 births, 7 deaths`) вместо потока одиночных
- **Event stream API**: SSE или WebSocket endpoint, который любой клиент (text viewer, 2D, 3D) может consume одинаково
